# План перехода: /d (d1) → /d2 → cutover

Статус: **план, не реализовано**. Создан 2026-10-07; обновлён 2026-10-07 по решениям владельца: D2 = Grist + Telegram only; cutover по варианту X (старый Postgres-редактор сносится), выполняется ночью.
Код не тронут; всё ниже — только дизайн перехода.

> **Как работать по этому плану.** Сессия-обсуждение никаких правок кода не
> делает — только этот документ. Реализация — в отдельных сессиях, по одной
> задаче из чек-листа, в порядке этапов 0 → 1 → 2. Новая сессия читает этот
> файл и берёт ровно одну задачу.

## Решения владельца (2026-10-07, вторая итерация плана)

1. **Файлы d2 — в гит с самого начала.** Исключение `templates/d2_*` в
   `.gitignore:138` было временной мерой на время подготовки ветки; ветка
   `attid/d2` теперь основная для этой работы. Шаблоны и этот план-ТЗ
   коммитятся первой же задачей.
2. **D2 работает ТОЛЬКО с Grist и Telegram.** Google Sheets и Postgres в
   новый поток не входят: ни чтения, ни записи. Новый вопрос живёт только в
   Grist (`QUESTIONS` + `QUESTION_DATA`). Postgres остаётся архивом старых
   вопросов (вся старая база уже перелита миграцией `migrate_decisions_to_grist()`).
3. **Мёрж master заранее не нужен.** Ветку делаем около недели, master уйдёт
   вперёд на десятки комитов — мёржим по ходу/перед cutover, отставание не
   проблема.
4. **Cutover по варианту X, ночью.** После cutover все старые вопросы
   редактируются в новом интерфейсе по старому адресу: `/d/<uuid>` отдаёт
   Grist-экран, старый Postgres-редактор удаляется целиком. Окно cutover —
   ночь, когда вопросами не пользуются.

## Решённый вопрос: судьба старого редактора `/d/<uuid>`

**Решение: вариант X, cutover ночью.** После cutover `/d/<uuid>` отдаёт тот же
Grist-экран, что и `/d2/<uuid>`: просмотр + правка текста/статуса в Grist +
`edit_message_text` в TG по `TELEGRAM_LINK`. Старый Postgres-редактор
(`cmd_show_decision`, `decision.py:226-352`) удаляется целиком — вместе с ним
умирают рассинхрон Postgres/Grist и вопрос «какой источник истины».
Postgres остаётся нетронутым архивом, ссылки `/d/<uuid>` не меняются.

Требование к задаче 1 отсюда: Grist-экран должен покрыть ВСЕ возможности
старого редактора (правка текста/статуса/чтения, TG-правка поста) — иначе
после cutover старым вопросам некуда деться. Проверить по коду
`decision.py:226-352` при реализации.

## Целевой сценарий перехода

1. Этап 0: дописать d2 на `/d2` до рабочего состояния (Grist + TG only).
2. Этап 1: пилот — один реальный вопрос через `/d2`, полный цикл.
3. Этап 2: cutover — `/d2` переименовать в `/d` (конструктор), старое создание
   и старый Postgres-редактор убрать (вариант X), окно — ночь.
4. Deep-links старых вопросов (`/d/<uuid>`) не меняются ни в каком варианте.

## Этап 0 — дописать d2 (безопасно, до пилота)

- **0. Забрать файлы в гит:** убрать `templates/d2_*` из `.gitignore:138`;
  закоммитить шаблоны `templates/d2_*` и этот план в `attid/d2`.
- `cmd_d2_index()` (`decision.py:151-154`): при `question_uuid` показывать сам
  вопрос — просмотр + форма редактирования при правах подписанта, **данные из
  Grist** (`QUESTION_DATA` по `UUID`), не делегация в `cmd_show_decision`
  (та читает Postgres). Правка вопроса: апдейт Grist + `edit_message_text` в
  TG по `TELEGRAM_LINK`, если ссылка заполнена.
- `templates/d2_frag_edit.html`: ссылка на `/d/<uuid>` → заменяется на
  `/d2/<uuid>` (вопрос теперь открывается Grist-экраном).
- «Выбрать» в `templates/d2_frag_new.html`: выбор шаблона → форма нового
  вопроса (номер, тема, чтение, предзаполненный BODY из шаблона).
- POST-создание вопроса из d2 — **новый** обработчик:
  - гейт `check_user_weight()` — тот же, что на `/d`;
  - генерация `uuid4().hex`;
  - запись в Grist `QUESTIONS` + `QUESTION_DATA` (с `UUID`, `CREATED_BY`);
  - публикация в TG (`skynet_bot.send_message`) в чат чтения;
  - обратная запись `TELEGRAM_LINK` в Grist-строку.
  - **Порядок: Grist → TG → Grist(link).** Фейл Grist: ничего не ушло, юзер
    ретраит. Фейл TG: вопрос создан, публикации нет — юзеру показываем ошибку
    и `uuid`, публикация вручную/ретрай без дубля в Grist.
  - **Без Google Sheets и без Postgres.** Google Sheet `MTL_decisions` после
    пилота перестаёт пополняться новыми вопросами — принято владельцем.

## Этап 1 — пилот на одном вопросе

- Создать вопрос с очевидным тестовым номером через `/d2`.
- Проверить: появился в списке `/d2/fragment/edit`; TG-публикация ушла в
  правильный чат чтения; `QUESTION_DATA.UUID` и `TELEGRAM_LINK` заполнены;
  `/d2/<uuid>` открывает и редактирует вопрос; правка статуса доезжает до
  TG-поста (`edit_message_text`).

Критерий: пилотный вопрос проходит полный цикл (создание → список → открытие →
правка) без ручных правок в Grist и без Postgres.

## Этап 2 — cutover (ночь, вариант X)

- Старый d1-конструктор вырезается: `cmd_add_decision`
  (`decision.py:57-141`) — форма и POST — удаляются.
- Конструктор с `/d2` занимает `/d`; `/d2` остаётся редиректом на `/d`.
- `/d/<uuid>` и `/d2/<uuid>` — один Grist-экран; старый Postgres-редактор
  (`cmd_show_decision`, `decision.py:226-352`) удаляется.
- Никаких переименований таблиц/данных — только маршруты и шаблоны.

## Этап 3 — не нужен

При варианте X переходный месяц отсутствует: после cutover один экран на
Grist, все вопросы (старые и новые) правятся в новом интерфейсе по своим
адресам. Postgres-копия тихо устаревает как архив.

## Риски

- Расхождение Grist с реальностью при создании вне d2 — после cutover новый
  путь создания один, риск закрывается.
- Частичный отказ при создании (TG упал после Grist) — вопрос создан без
  публикации; форма показывает uuid; повторная публикация без дубля в Grist.
  Догонять вручную или отдельной кнопкой — решим при реализации задачи 2.
- Шаблоны в `.gitignore` — риск снят решением 1 (этап 0, задача 0).

## Чек-лист задач для сессий-реализаций

Порядок строгий: 0 → 1 → 2 → 3 → 4 (пилот) → 5 (cutover). Одна сессия — одна
задача.

0. **Файлы d2 в гит** — убрать `templates/d2_*` из `.gitignore:138`,
   закоммитить шаблоны и этот план. Приёмка: шаблоны и план в ветке `attid/d2`,
   в гит-статусе чисто.
1. **Экран вопроса `/d2/<uuid>` на Grist** — GET: просмотр из
   `QUESTION_DATA`+`QUESTIONS` по `UUID` (просмотр открыт, правка — по
   `check_user_weight()`); POST: апдейт Grist + `edit_message_text` в TG по
   `TELEGRAM_LINK`. Приёмка: старый мигрированный вопрос открывается и
   редактируется по `/d2/<uuid>`, правка доезжает до TG-поста.
2. **Форма создания из шаблона + POST** — фрагмент-форма (тема, номер,
   чтение, предзаполненный BODY из шаблона); кнопка «Выбрать» в
   `d2_frag_new.html` грузит её. POST: гейт `check_user_weight()`,
   `uuid4().hex`, Grist `QUESTIONS`+`QUESTION_DATA` → TG-пост →
   `TELEGRAM_LINK` обратно в Grist. Без Google Sheets и Postgres.
   Приёмка: созданный через `/d2` вопрос виден в списке, открывается по
   `/d2/<uuid>`, TG-пост в правильном чате.
3. **Список редактирования** — `cmd_d2_edit` принимает `uuid` (подсветка
   строки), в `d2_frag_edit.html` ссылка на `/d2/<uuid>`. Приёмка: из списка
   кликом попадаешь на вопрос и обратно.
4. **Пилот** — один реальный вопрос через `/d2` полный цикл (создание →
   список → `/d2/<uuid>` → правка с `edit_message_text`), без ручных правок
   в Grist. Приёмка: критерий этапа 1.
5. **Cutover (ночь)** — вырезать `cmd_add_decision` (`decision.py:57-141`)
   и `cmd_show_decision` (`decision.py:226-352`), маршрут `/d` отдать
   конструктору d2, `/d2` → редирект на `/d`, `/d/<uuid>` → Grist-экран
   (тот же, что `/d2/<uuid>`). Приёмка: старые `/d/<uuid>` открываются и
   редактируются в новом интерфейсе, новые вопросы создаются только
   по-новому.
