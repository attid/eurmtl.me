# План перехода: /d (d1) → Grist → /d2 UX (план B)

Статус: **в работе**. Создан 2026-10-07; третья итерация по решениям
владельца: D2 = Grist + Telegram only; порядок — сначала данные (Postgres →
Grist, ночью), потом UX d2 поэтапно и без дедлайна.
Задача 0 выполнена (коммит `fdeed9d` в `attid/d2`).
Задачи 1–4 выполнены (стенд `dbd2f61`+`121b903`; экран `/d2/<uuid>`,
создание `/d2/add`, список — коммит задач 2–4). Осталось: 5 (пилот),
6 (ночь), 7 (UX).

> **Как работать по этому плану.** Сессия-обсуждение никаких правок кода не
> делает — только этот документ. Реализация — в отдельных сессиях, по одной
> задаче из чек-листа, по порядку. Новая сессия читает этот файл и берёт
> ровно одну задачу.

## Решения владельца (2026-10-07, хронология)

1. **Файлы d2 — в гит с самого начала.** Исключение `templates/d2_*` в
   `.gitignore:138` было временной мерой; ветка `attid/d2` — рабочая. —
   Выполнено, коммит `fdeed9d`.
2. **D2 работает ТОЛЬКО с Grist и Telegram.** Google Sheets и Postgres в
   новый поток не входят: ни чтения, ни записи. Postgres остаётся архивом
   (вся старая база уже перелита миграцией `migrate_decisions_to_grist()`).
3. **Мёрж master заранее не нужен.** Ветку делаем около недели, мёржим по
   ходу/перед ночной фазой.
4. **Все старые вопросы редактируются в новом интерфейсе по старому адресу**
   (бывший вариант X): после переключения `/d/<uuid>` отдаёт Grist-экран,
   старый Postgres-редактор удаляется целиком.
5. **Порядок — данные сначала, UX потом (план B).** Ночью переключаем
   только нутро: `/d/<uuid>` и POST `/d` переезжают на Grist-обработчики при
   старом UI. Фрагмент-форма d2 занимает `/d` позже, отдельной задачей, без
   дедлайна.

## Почему план B (обоснование)

- Ночной переключатель минимальный: пользователь видит тот же UI, меняется
  хранилище. Радиус отказа ночью — один «шов», а не данные+маршруты+шаблоны.
- UX после ночи досыпается по кускам, каждый кусок обратим и не имеет
  дедлайна.
- Рассинхрон Postgres/Grist умирает в первую же ночь, а не живёт до конца
  недели.
- Дешевизна: Grist-экран вопроса использует тот же `tabler_decision.html`,
  что старый редактор; «перенос интерфейса» — это подмена обработчиков, а не
  новых экранов.

## Целевая схема Grist (лок этой итерации)

Док `hpZWKq729vw2D5AkG7oYYz` (`grist_tools.py:38-42`), хост `grist.eurmtl.me`.
Структура уже финальная под новый мир, доливок не требуется:

- `QUESTIONS`: `id, NUMBER, TITLE` (+ `READING` — максимальное чтение,
  проставлено миграцией).
- `QUESTION_DATA`: `id, QUESTION_ID → QUESTIONS, READING, UUID, TELEGRAM_LINK,
  BODY, STATUS, EXTRA, CREATED_BY → SP_USERS, CREATED_AT`.
  Одна строка = одно чтение вопроса. `EXTRA` — свободное поле на
  непредвиденное.
- `QUESTION_TEMPLATES`: `id, TITLE, BODY` — источники для фрагмент-формы.
- `SP_USERS`: матчинг автора по `USERNAME` без `@`, lowercase (алгоритм
  миграции `decision.py:437-442`).

Чат чтения: хардкод `chat_ids` (`decision.py:37-40`), как сейчас.
`SP_CHATS` — опция на потом, схему вопросов не трогает.
Номер нового вопроса: `max(QUESTIONS.NUMBER)+1` (сейчас берётся из Google
Sheets через `gs_get_last_id`, `/decision/number` — умирает вместе с Sheets).

## Целевой сценарий

1. Фаза 1 (дни): тестовый стенд (задача 1), затем Grist-обработчики пишем и
   обкатываем на побочном пути `/d2/<uuid>` и `/d2` — старый `/d` живёт как
   жил, UX проверяется на стенде.
2. Фаза 2 (одна ночь): только данные — `/d/<uuid>` и POST `/d` репоим на
   Grist-обработчики, старый UI сохраняется, Postgres-ветки удаляются, перед
   переключением догон миграции.
3. Фаза 3 (после ночи, без дедлайна): UX d2 — фрагмент-форма из шаблона
   заменяет старую форму создания, старую удаляем.
4. Deep-links `/d/<uuid>` не меняются ни на одном шаге.

## Чек-лист задач для сессий-реализаций

Порядок строгий: 1 (стенд) → 2 → 3 → 4 → 5 (пилот: стенд + прод) → 6 (ночь)
→ 7 (UX). Одна сессия — одна задача.

1. **Тестовый стенд (Grist-двойник + TG-мок)** — среда для ручного
   тыканья d2 без Grist-сервера и Telegram, цель — отловить UX-ошибки до
   заливки на сервер.
   - **Основание уже есть:** `ENVIRONMENT≠production` → `config.test_mode`
     (`config_reader.py:51-58`); `update_test_user()` (`start.py:53-68`)
     подставляет фейковую сессию itolstov — залогинен всегда; в тест-режиме
     `app.run(debug=True)` на `:8000` (`start.py:125-128`); grist-кеш не
     инициализируется (`start.py:121-124`); в pytest давно SQLite in-memory
     (`tests/fixtures/database.py`).
   - **Затык 1 — Grist:** `grist_manager` (`grist_tools.py:382`) ходит HTTP
     в `grist.eurmtl.me`. Для стенда — Grist-двойник: in-memory таблицы
     `QUESTIONS/QUESTION_DATA/QUESTION_TEMPLATES/SP_USERS` + мини-Quart
     приложение, отдающее `GET/POST/PATCH /docs/{doc}/{table}` в формате
     Grist API (свериться с `fetch_data/patch_data/post_data`,
     `grist_tools.py:76-192`). Сид данных — отдельный файл-фикстура,
     правится под сценарий (пустой Grist, вопрос без чтений и т.д.).
     В тест-режиме `grist_manager` биндится на двойник (подмена base_url).
   - **Затык 2 — TG:** в тест-режиме `skynet_bot.send_message/edit_message_text`
     мокаются: фиктивный `message_id`, вызовы пишутся в лог/JSON. Страница
     `/dev/tg-log` (только тест-режим) показывает опубликованные тексты —
     «что бы улетело в TG» глазами.
   - **Запуск стенда:** `ENVIRONMENT=test uv run python start.py` →
     `localhost:8000`, тыкать `/d2`. Прод не задет: `test_mode` уже отрезает
     Sentry/кеш/бота.
   - Двойник и TG-мок делаются как pytest-фикстуры — переиспользуются
     автотестами задач 2–6 вместо разрозненных моков.
   - Приёмка: стенд поднимается одной командой, полный цикл d2 тыкается
     браузером, TG-публикации видны на `/dev/tg-log`.
2. **Экран вопроса `/d2/<uuid>` на Grist** — замена заглушки
   `cmd_d2_index` (`decision.py:149-154`): `/d2` остаётся лендингом,
   `/d2/<uuid>` — новый GET+POST роут.
   - GET: `len(uuid)!=32` → 404; джойн `QUESTION_DATA` (по `UUID`) +
     `QUESTIONS` (по `QUESTION_ID`); `tabler_decision.html`:
     `short_subject=QUESTIONS.TITLE`, `inquiry=QUESTION_DATA.BODY`,
     `reading=QUESTION_DATA.READING`, `status=QUESTION_DATA.STATUS`,
     `links_url` — из всех `QUESTION_DATA` того же `QUESTION_ID`
     (индекс = чтение−1), `user_weight` (просмотр открыт всем).
   - POST (гейт `check_user_weight()`): `short_subject` → patch
     `QUESTIONS.TITLE`; `inquiry` → patch `QUESTION_DATA.BODY`; `status` →
     patch `QUESTION_DATA.STATUS`; затем `edit_message_text` в
     `chat_ids[reading]`, `message_id` из `TELEGRAM_LINK.split("/")[-1]`.
   - Смена чтения: `links_url[reading-1]` занято → flash «уже существует»;
     иначе создание новой строки `QUESTION_DATA` (новый `uuid4().hex`, тот же
     `QUESTION_ID`, `READING`, `BODY`, `STATUS`, `CREATED_BY` по `SP_USERS`),
     TG `send_message` → `TELEGRAM_LINK` в новую строку; рендер той же формы
     с новыми данными (без redirect).
   - Отказ TG после patch Grist: flash «Ошибка публикации в Telegram», данные
     в Grist сохранены (источник истины Grist, не откатываем).
   - `templates/d2_index.html`: убрать htmx-хвост `hx-get="/d2/fragment/edit?uuid=…"`
     по `load` (deep-link теперь самостоятельный экран).
   - Тесты: фикстуры стенда из задачи 1 (Grist-двойник, TG-мок) +
     `check_user_weight`.
   - Приёмка: старый мигрированный вопрос открывается и редактируется по
     `/d2/<uuid>`, правка доезжает до TG-поста.
3. **POST-создание вопроса (логика Grist+TG, рендер старой формы)** —
   ключевой трюк плана B: новая логика, **старый UI**. Роут `/d2/add`
   (побочный путь) рендерит `tabler_decision.html` в режиме создания (как
   `cmd_add_decision`, `decision.py:57-141`, но данные — Grist).
   - Номер: `max(QUESTIONS.NUMBER)+1`.
   - POST: гейт `check_user_weight()`; `uuid4().hex`; post `QUESTIONS`
     (NUMBER, TITLE, READING) → post `QUESTION_DATA` (UUID, TELEGRAM_LINK
     пока пусто, BODY, STATUS, EXTRA="", CREATED_BY, CREATED_AT) →
     TG `send_message` → patch `TELEGRAM_LINK`.
   - Порядок отказа: фейл Grist — ничего не ушло, ретрай; фейл TG — вопрос
     создан без публикации, flash + uuid, публикация ретраем без дубля.
   - Приёмка: созданный через `/d2/add` вопрос открывается по `/d2/<uuid>`,
     TG-пост в правильном чате, число в Grist совпадает.
4. **Список редактирования** — `cmd_d2_edit` принимает `uuid` (подсветка
   строки), в `d2_frag_edit.html` ссылки на `/d2/<uuid>`. Приёмка: из списка
   кликом попадаешь на вопрос и обратно.
5. **Пилот** — стенд из задачи 1: полный цикл `/d2/add`: создание → список →
   `/d2/<uuid>` → правка с `edit_message_text`. Без ручных правок в
   Grist-двойнике, TG-публикации проверяются на `/dev/tg-log`. Затем один
   реальный вопрос на проде — финальная приёмка.
   Приёмка: полный цикл на Grist-логике со старым UI, UX-косяки пойманы на
   стенде до сервера.
6. **Ночь: переключение данных (вариант X)** — перед началом догон
   `migrate_decisions_to_grist()` + сверка количества строк Postgres vs Grist.
   Затем:
   - `GET+POST /d/<uuid>` → тот же Grist-обработчик, что `/d2/<uuid>`
     (задача 2);
   - `GET+POST /d` (создание) → Grist-логика задачи 3, UI прежний;
   - удалить `cmd_show_decision` (`decision.py:226-352`) и Postgres-ветки
     `cmd_add_decision`;
   - `/decision/number` (`gs_get_last_id`) — удалить или репоим на
     `max(NUMBER)+1` (решить по месту, кто его дёргает);
   - `/d2` и `/d2/<uuid>` остаются как есть (побочный путь).
   - Приёмка: старые `/d/<uuid>` открываются и редактируются (UI тот же,
     хранилище Grist), новые вопросы создаются через `/d` и живут в Grist,
     в Postgres ничего не пишется.
7. **UX-фаза: форма создания из шаблона** (после ночи, без дедлайна) —
   фрагмент-форма (тема, номер, чтение, предзаполненный BODY из
   `QUESTION_TEMPLATES`), кнопка «Выбрать» в `d2_frag_new.html` грузит её;
   POST — та же логика задачи 2. Фрагмент-форма занимает `/d` (создание),
   `/d2` — редирект на `/d`; старую форму создания удалить. Приёмка:
   создание по `/d` работает через фрагмент-форму из шаблона.

## Риски

- Тестовый стенд может разойтись с реальным Grist API (неучтённый формат
  ответа) — двойник пишем строго по формату `fetch_data/patch_data/post_data`
  (`grist_tools.py:76-192`); пилот на проде (задача 5) ловит расхождение до
  ночной фазы.
- Вопросы, созданные через старый `/d` после прошлой миграции, отсутствуют в
  Grist — закрывается догоном миграции перед ночью (задача 6) + сверка
  количества строк.
- Номер вопроса: гонка двух одновременных созданий — теоретическая для фонда;
  при коллизии ретрай.
- Частичный отказ при создании (TG упал после Grist) — вопрос создан без
  публикации; flash + uuid; повторная публикация без дубля в Grist.
- Поиск строки `QUESTION_DATA` по `UUID` — полный скан `load_table_data`
  (`find_by_uuid` у `grist_manager` нет); на текущих объёмах ок, усложнение
  не тащим.
